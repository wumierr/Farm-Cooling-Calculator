## 1. 代码质量与结构评估

### 1.1 值得肯定的部分

- **分层清晰**：`src/lib/calculator/`（纯函数引擎：`types / presets / engine / advice / multi-day`）与 `src/components/calculator/`（React 视图）彻底分离。引擎无副作用、可测试、可在 Node 里直接跑（本次评估正是这么验证的）。
- **类型完备**：`types.ts` 定义了全部数据结构，单位在注释里显式标注，避免隐式换算。
- **算法注释到位**：`engine.ts` 顶部记录了相对原始 HTML 版的 5 处修复，可追溯。

### 1.2 主要问题与改进建议

**(A) 依赖臃肿 —— 最值得动手的一处** 〔P0/P1〕

扫描 `src/` 全量 import，实际被引用的运行时依赖只有：`recharts / zustand / next-themes / sonner / lucide-react` + shadcn 用到的部分 `@radix-ui/*` + `clsx / tailwind-merge / class-variance-authority`。

以下依赖在 `src/` 中**零引用**，属脚手架模板遗留，可直接删除：

```
z-ai-web-dev-sdk      @mdxeditor/editor        react-syntax-highlighter
next-auth             next-intl                @tanstack/react-query
@tanstack/react-table react-hook-form          @hookform/resolvers
@dnd-kit/core         @dnd-kit/sortable        @dnd-kit/utilities
embla-carousel-react  vaul   cmdk   input-otp  react-day-picker
framer-motion         react-markdown           date-fns
uuid                  zod                       @reactuses/core
prisma  @prisma/client（仅 src/lib/db.ts 引用，而 db.ts 全项目无人调用）
```

- **收益**：`node_modules` 体积与首次 `bun install` 时间大幅下降（当前文档写"约 700MB / 1~3 分钟"）；**同时显著缩小与 React 19 / Next 16 的 peer-dependency 冲突面**——这正是版本报错的温床之一。
- **注意**：删除 dep 的同时必须删掉引用它的未使用 shadcn 组件文件（如 `ui/calendar.tsx`→react-day-picker、`ui/carousel.tsx`→embla、`ui/form.tsx`→react-hook-form、`ui/command.tsx`→cmdk、`ui/drawer.tsx`→vaul、`ui/input-otp.tsx`、`ui/sidebar.tsx`），否则静态导出会因找不到模块而失败。落地阶段会逐一 grep 确认后成对删除。
- **工具建议**：引入 `knip` 或 `depcheck` 做一次性未用依赖/导出体检（见 §6）。

**(B) `output-panel.tsx`（622 行）职责过载** 〔P1〕

单文件里塞了：`Warnings / OptimumCard / METRICS_META / DiffBadge / getAdviceForR / StrategyComparison / DetailRow / DetailRowWithBar / DetailTable / StrategyToggles / OutputPanel`。建议拆分：

- `getAdviceForR` 是纯计算，应下沉到 `lib/calculator/advice.ts`（与 `interpolateDilution` 逻辑重复，可合并去重）。
- `StrategyComparison`（Diff Grid）、`DetailTable`、`OptimumCard` 各自独立成文件。
- 收益：可读性、可测性、后续 UI 重构时改动面可控。

**(C) 重复的插值逻辑** 〔P2〕

线性插值在 `engine.ts::linearInterpolate`、`advice.ts::interpolateDilution`、`advice.ts::calcCostBenefitCurve`、`output-panel.tsx::getAdviceForR` 各写了一份（含 coverage 映射表也重复硬编码了两遍）。应统一走 `linearInterpolate`，`K_MODE_COVERAGE_MAP` 只留 `presets.ts` 一处。

**(D) store 全量重算** 〔P2，与移动端性能相关〕

`store.ts::recalculate` 每次参数变更都重跑 `findOptimalR`（71 点全扫）+ 策略提取 + 成本曲线。已有 350ms 防抖缓解，但可进一步：对 `findOptimalR` 按 `params` 做记忆化；成本效益曲线仅在经济参数变化时重算。详见 §3.3。

**(E) 魔法数字**：`getTableAdvice` 里 `getSprayerBatches(powderKg, waterL, 20, false)` 把喷雾器容量硬编码为 20（虽然 store 层事后用 `params.sprayerCap` 覆盖了 `batchInfo`，但 `advice.value` 文案里的分批仍可能基于 20）。建议直接传 `params.sprayerCap`，去掉"先算错再覆盖"的绕路。

### 2.2 APK 报错根因（系统性梳理）

你的机器环境（`docs/DEPLOY.md` 第 366–370 行自述）：**Node v20.17.0、JDK 17.0.3.1、SDK 未装（脚本自动装 android-35 / build-tools 35）**。

把它和 Capacitor 8 的要求对照，**三处硬冲突**：

1. **JDK 17 ≠ 21** → Gradle 编译 `:capacitor-android:compileDebugJavaWithJavac` 时报 `invalid source release: 21`。**这是最典型的"版本不兼容"报错。**
2. **SDK 35 ≠ 36** → AGP 8.13 要求 compileSdk 36，构建报 `Failed to find target with hash string 'android-36'` 或提示需要更高 compileSdk。
3. **Node 20 < 22** → `@capacitor/cli@8` 启动即告警/退出（"Capacitor 8 requires NodeJS 22 or greater"）。

### 2.3 打包脚本的两处独立缺陷

- **bash 路径 `apk-build/build-apk.sh` 第 48 行 `bun run build`**：会触发 `package.json` 的 `build` 脚本 `next build && cp -r .next/static .next/standalone/...`。而静态导出模式（`CAPACITOR_BUILD=1`）根本不产生 `.next/standalone/` 目录 → `cp` 失败 → `set -e` 直接中断。**Windows 的 `build-apk.ps1` 走 `build-static.ps1`（直接 `next build`）绕开了这个坑，所以两条打包路径行为不一致。**
- **`bun run build 2>&1 | tail` 吞退出码**：`DEPLOY.md` 第 443 行自己都写了"管道让退出码变成 tail 的 0，构建失败也当成功继续跑"。应改 `set -o pipefail` 或去掉管道。

### 2.4 推荐修复方案（二选一）

**✅ 方案 B（推荐，改动最小、最稳）：降到 Capacitor 7**

- `@capacitor/{core,cli,android}` → `^7`（脚本**已经**在装 SDK 35 / build-tools 35，与 Cap7 天然吻合，几乎零额外改动）。
- 只需：把脚本/文档的 **JDK 要求从 17 改成 21**（Temurin 21，或随新版 Android Studio 附带）。Node 保持 18+ 即可。
- 删除 `@ea-utilities/build-capacitor`（非官方封装、仅 bash 路径用到，是额外的版本冲突源），bash 路径改为和 ps1 一样直接调用 `gradlew assembleDebug`。
- `android/` 工程是 `cap add android` 现场生成、且未入库，重建完全干净、无历史冲突。

**方案 A（追新）：留在 Capacitor 8，把环境全部对齐**

- Node 升 22、JDK 升 21、脚本把 `platforms;android-35 build-tools;35.0.0` 改为 `android-36 build-tools;36.0.0`。
- 适合愿意用最新 Android Studio（Otter 2025.2.1+）的场景；命令行打 debug 包不强制装 Studio，但 SDK 36 组件必须齐。

> **两种方案我都会在落地阶段写成"改脚本 + 改文档 + 给你本机可复制命令"**。因为云端沙箱装不了安卓 SDK/Gradle，最终 `gradlew assembleDebug` 必须在你本机执行——我会保证网页端/静态导出这一段在改动后可正常构建，把 Android 段的命令和前置检查交给你一键跑。

## 3. 核心计算模型再评估

### 3.1 现有模型逐项体检

| 子模型 | 实现 | 评价 | 建议 |
|--------|------|------|------|
| 逐时气温 | 白天分段正弦 `dayShape`，夜间恒 Tmin | 合理，支持非对称峰值 | 保留 |
| 降温量 | `dT(h)=dTmax×(baseFrac+sd·0.5·solar(h))`，日照加权 | 比原版恒定降温更真实 | 保留；`SOLAR_DEPENDENCE=0.6` 可作为高级参数暴露 |
| HHA | 二次方 `(T−T0)²×湿度因子×步长` | 经验模型，阈值来自设施葡萄热害研究 | 保留；阈值可做敏感性说明 |
| 产量损失 | 三段线性查 HHA→L | 简单可解释 | 保留 |
| 光合 | Michaelis–Menten + LSP 饱和钳位 + 步长积分 | 物理正确 | 见 §3.2 |
| 光谱 | Fritsch–Carlson 单调样条 + 73 点积分 | 数值稳健、不过冲 | 保留；已做 O(1) 预计算优化 |
| 优化 | R∈[0.10,0.80] 步长 0.01 全扫 71 点，取近优平台下限 | 省钱导向，合理 | 见 §3.3 |

**离线复算验证**（本次用 Node 直接跑真实 `engine.ts`）：默认场景（克瑞森，Tmax 45℃）得 **最优 R=29%、Y=0.9693、降温后棚温 41℃、近优平台 29–65%、不施用基准 L=33.5%**——与 worklog 记录完全一致，引擎数值可信。

### 3.2 拟合方式：是否有更优替代？

现用 Michaelis–Menten（直角双曲线）。农学界更常用**非直角双曲线（Non-rectangular hyperbola）**拟合光响应曲线，它多一个曲率参数 θ，在 LSP 附近过渡更自然，对"接近饱和但未饱和"的中等遮阳区间更准。

- **取舍建议（符合你"允许非关键降精度换性能"的原则）**：主计算引擎**不必**换——±5% 精度对田间决策足够，直角双曲线更快更稳。但**新的可视化面板（§5）**正好可以把"直角双曲线 / 非直角双曲线 / 含光抑制"作为**可切换模型**展示给用户看形态差异，既满足教学直观，又不动主引擎。这是"更优拟合"落点最合适的地方。

### 3.3 移动端算力与实时性优化

- **记忆化 `findOptimalR`**：以 `params` 浅哈希为 key 缓存最近 1–3 次结果，避免 A/B 对比、图表联动时重复全扫。
- **成本效益曲线按需算**：`calcCostBenefitCurve` 仅在 `powderPrice/grapePrice/expectedYield/sprayArea` 变化时重算，其余参数变化复用。
- **R 搜索自适应粒度（可选）**：先 0.02 粗扫定位峰区，再在峰区附近 0.005 精扫——点数从 71 降到 ~45，移动端更跟手；属"非关键降精度"范畴。
- **样条积分**：已做基曲线一次样条 + O(1) 线性缩放，无需再改。
- 结论：**算法本身不需要重写**，优化重点是"少算、缓存、按需"，而非改数学。

## 4. UI/UX 重构方案（整体视觉重构）

### 4.1 现状问题

- 信息密度过高：`text-[9px]`/`text-[10px]` 大量出现，田间强光/手机上难读。
- 窄屏体验：主布局 `lg:grid-cols-[420px_1fr]`，在 `<lg` 变单列纵向堆叠，输入区很长、要滚很久才到结果；策略对比 Grid 靠横向滚动挤在窄屏。
- 视觉层级偏弱：卡片密集、留白不足、强调色（琥珀）用得零散。
- 平板/PC 宽屏没有充分利用横向空间（内容被 `max-w-[1600px]` 限宽后中间大量卡片仍是窄列）。

### 4.2 新设计方向

**响应式 App Shell（核心）**

- **宽屏（≥1024px，平板横屏/PC）**：左侧固定输入栏（可折叠）+ 右侧主工作区，主工作区用**分区卡片网格**（结果卡 / 曲线 / 新光合面板 / 策略对比 / 处方明细）二列自适应铺满，不再是单窄列。
- **窄屏（<1024px，手机竖屏）**：改为**底部/顶部 Tab 导航**——`参数` / `结果` / `图表` / `处方` 四个 Tab，每屏只专注一件事，避免超长滚动。横竖屏切换时按断点自动重排。
- 组件库：继续用 shadcn `Tabs`（已在依赖内），无需新增依赖。

**主题令牌升级**

- 保留农业绿+暖琥珀基调，但重排 `oklch` 令牌：提高浅色模式对比度、统一强调色使用规则（主色=行动/最优，琥珀=近优/提示，红=风险）。
- 排版尺度：最小正文提到 `12px`（`text-xs`），关键数字用 `tabular-nums` + 更大字号；去掉 `9px` 极小字。
- 一致的圆角/阴影/间距比例（4/8/12/16 网格），卡片统一 elevation。
- 动效：入场 `fade-in`、数值变化 `value-change`（已有），补充 Tab 切换过渡。

### 4.3 落地策略（低风险）

为在无法云端编译的前提下把破坏风险降到最低，重构以**外壳与样式为主、业务逻辑零改**：

1. 重写 `globals.css`（新主题令牌 + 排版尺度 + 动效）。
2. 重写 `calculator-client.tsx`（新 App Shell + 响应式 Tab/分栏）。
3. 输入/输出面板内部逻辑保持不变，仅按新令牌做 className 级微调。
4. 新增光合面板作为独立组件挂进布局（§5）。
5. 你本机 `bun run dev` 逐屏回归（我会给检查清单）。

## 5. 新增数据可视化面板：一天内光照 → 光合转化效率

### 5.1 概念

横轴＝一天时刻（日出→日落），纵轴＝该时刻**瞬时光能转化效率**（0–1，冠层光合速率相对峰值）。曲线下方阴影＝**全天累计效能（积分面积）**，直观对应引擎里真正积分的那个量 `A`。

### 5.2 可切换的三种"算法策略/模型"（形态差异）

已用离线原型跑通（Node 复算，真实 `dayShape` + 光响应）：

| 模型 | 机理 | 形态 | 全天积分面积（原型值） |
|------|------|------|------------------------|
| 光限制型 | 效率≈正比光强（未饱和） | **单峰**，正午尖 | 10.25 |
| 光饱和型 | Michaelis–Menten + LSP 饱和 | **平台**，正午封顶变平 | 13.30 |
| 光抑制型 | 正午强光光抑制/气孔午休 | **双峰**（午休凹陷） | 9.28 |

三种形态肉眼可辨，正好对应需求里的"单峰 / 平台 / 双峰"。用户切换即可看到同样的光照输入在不同生理假设下"能利用多少光"，并用积分面积横向比较全天效能。

### 5.3 交互

- 触摸/悬停查看某时刻的具体效率数值 + 当时 PAR。
- 缩放：Recharts `Brush` 组件框选时段放大（移动端可拖动）。
- 与主参数联动：随 `Imax / D / LSP / LCP / 当前遮阳率 R` 实时更新（遮阳会压低进光、改变是否触顶）。
- 面积高亮：可切换"是否叠加不施降温剂 vs 施用后"两条曲线对比全天光合总量的变化。

### 5.4 实现

- 新组件 `src/components/calculator/light-response-chart.tsx`，Recharts `ComposedChart`（`Area` 画积分面积 + `Line` 画效率曲线 + `Brush` 缩放 + `ReferenceLine` 标正午/LSP 触顶点）。
- 计算下沉到 `lib/calculator/light-response.ts`（纯函数，含三模型 + 积分），可单测、可在 Node 复算。
